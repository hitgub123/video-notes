## 总结

### 为什么代码审查是最高杠杆的工程活动

课程开篇的论点很直接：代码审查（code review）是成为更好的工程师、提升团队整体代码质量的最高杠杆活动之一，而且有数据支撑（课件引自 Coding Horror 汇总的研究）：

- 代码审查的错误检出率是 **55–60%**，而各种测试模式的检出率只有 25–45%
- 一项对比研究里，有代码审查的程序错误率从 4.5 降到 **0.82 个错误 / 100 行**
- AT&T 的研究显示，引入代码审查带来 **14% 的生产力提升**和 **90% 的缺陷减少**

也就是说，审查不是上线前的形式关卡，而是检出效率明显高于测试的一道质量防线。

### 审查应该抓什么：五个维度

课件列出审查要抓的五类问题：

- **逻辑与正确性错误**——代码是否按预期工作，边界条件、off-by-one 之类有没有处理错
- **可读性与可维护性**——是否易于理解和后续修改，命名是否清晰，函数职责是否单一
- **性能**——有没有不必要的数据库查询、N+1 问题、不合理的时间/空间复杂度
- **安全**——SQL 注入、XSS、未验证的输入、敏感数据泄露等隐患
- **最佳实践**——是否遵循项目的编码规范、设计模式和架构约定

### 什么是好的审查意见

课件用一组对照点出关键：只写一句 "This won't work"（这不行）不是好的审查意见——它不提供任何教学价值。好的意见是建设性的、具体的，并邀请对方一起讨论。课件给的范例大意是：

> 我注意到你新写的方法沿用了这个文件里已有的风格，带了 [X] 个参数。参数这么多会损害可读性，也暗示这个函数做的事情太多了。你觉得怎么样——要不要在后续的一个 PR 里，把这个方法和已有的几个方法一起重构，减少它们的参数数量？

注意这个范例的姿态：先认可作者与现有代码风格的一致性，再指出问题和理由，最后把改进提议成一个可以商量的后续动作，而不是当场命令。

### 审查质量首先取决于 PR 质量

讲义补充了一个很实际的观点：很多所谓"低质量审查"，根源并不在审查者，而在 pull request 本身——过大、上下文不足、变更意图不清晰。要让审查有效，团队得先把 PR 设计成一个"可审查的对象"：

- 控制单个 PR 的规模，让审查者能在有限时间内建立完整的心智模型
- 提供变更背景：问题是什么、为什么现在改、有没有考虑过替代方案
- 写清验证方法：跑了哪些测试、有哪些已知风险
- 大改动用堆叠式 diff（stacked diffs）或按主题拆分，不要一次性提交

讲义里一句话总结：审查效率不是审查者一个人的 KPI——如果作者交上来的是一个 3000 行、跨十个模块、没有任何说明的 PR，再强的审查者也只能给出表层反馈。高效审查是作者、工具和审查者共同设计出来的流程能力。

### 审查意见的三层结构

承接上面的"好意见长什么样"，讲义把一条好的审查评论拆成三层：

1. **观察**：指出具体的代码或行为
2. **原因**：解释为什么这会造成风险、复杂度或歧义
3. **建议**：给出替代方案、提问路径或后续改进方向

资深团队往往把代码审查看成设计讨论的最后一道关口，而不是上线前的抱怨区。评论最有价值的部分通常不是指出 bug，而是帮作者看到设计上的长期成本——审查从"挑错"变成"共同设计"。

### AI 代码审查的新世界

本周的嘉宾讲座来自 Graphite（CPO Tomas Reimers 主讲）。课件列出的 AI 代码审查工具包括：

- **Graphite**——本周嘉宾所属公司
- **Greptile**——主打基于代码库理解的 AI 审查
- **CodeRabbit**——自动化 PR 审查
- **Claude Code / Codex**——通用 AI 编码工具也可用于审查

AI 审查带来的改变，课件归纳为六点：**效率**（自动化处理常规检查，缩短审查周期）、**一致性**（对所有代码应用同一套标准）、**知识共享**（AI 可以携带整个代码库的上下文）、**减轻认知负担**（让人类专注于复杂逻辑和架构决策）、**持续改进**（系统随数据积累而变好）、**整体理解**（从全局视角审视变更的影响）。

由此形成一条分工原则：让 AI 处理"表层"问题（格式、命名、常见 bug 模式、安全检查），让人类专注"深层"问题（架构合理性、业务逻辑正确性、长期维护性）。

### AI 审查的局限——以及为什么审查反而更重要了

课件对局限讲得很坦率：

- 需要更多的配置和设置成本，要花时间"训练"系统
- 有**假阳性**（false positives），需要靠持续学习来压低误报
- 还抓不住仓库特有的惯用法（idioms）和最佳实践
- 处理不了复杂的业务逻辑和架构决策——但这正是人类仍然被需要的地方
- 对安全相关的变更必须格外谨慎
- 经常漏掉边界情况

最重要的一条结论：**有了 AI 编程系统之后，代码审查比以往任何时候都更重要**——因为合并和发布出去的代码是你自己的责任，不能怪 AI（"the AI wrote it" 不是免责借口）。
