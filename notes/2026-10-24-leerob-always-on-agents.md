## 总结

### 他讲的是什么

普通的编程 Agent 是"模型 + 工具循环"，关上笔记本进程就停了。这一代新产品（他以 SpaceX 内部的 Grok Bot 为例）是常驻型的：跑在云端服务器、有自己的一台 Linux 电脑、有文件和长期记忆、能被 Slack 消息、邮件、定时任务等事件唤醒，而且像同事一样知道什么时候该安静、只在有重要进展时才找你，目标是连续工作几周甚至几个月。

### 走到今天的四个阶段 + 模型的变化

从复制粘贴 ChatGPT 代码 → 终端编程 Agent → 独立 App 多 Agent 并行（但人要逐条审批命令，人是瓶颈）→ 常驻 Agent（改为"引导"而非"审批"，命令由另一个模型自动审查，他说这反而比人肉审批更安全）。

模型侧的关键进步有六点：长时指令跟随不出错；子 Agent 分工（各自带全新工作记忆，等于变相无限上下文）；工具调用成熟、幻觉基本被解决；能像人一样操作电脑界面（computer use，没有 API 的网站也能用）；一切信息存成文件供检索（画像、工作日志、记忆）；技能与例行任务可以沉淀复用（技能 = 把做事方法写成 Markdown 文件；例行任务 = 定时跑的提示词，本质是 cron）。

### 内部结构（干货最密的一段）

- 服务器和 Agent 的电脑平时都休眠，有触发才唤醒，状态全部存数据库——不然成本撑不住
- 唤醒源不只是用户发消息：SpaceX 已经有人派自己的 Bot 代替自己去开会做笔记；长任务跑完也会回来汇报
- 唤醒后有个路由器把事件放进对话，还有一个"要不要打扰用户"的判断——像同事一样，不是每有进展都来敲你
- Agent 的电脑是 Firecracker 虚拟机：可快照、可随时关停重建，还能给每个 Bot 开独立的虚拟桌面
- 架构是瘦客户端、胖服务器：客户端和服务器之间只有一个工具——"发送给用户"（send to user）；界面端负责把结果渲染成登录框、付款、待审批草稿、表情回应等富交互
- 长任务用 Temporal 这类**持久化工作流**：崩溃后从断点续跑，而不是从头重放步骤（普通任务队列做不到这点）
- 优先级：用户本人的消息可以打断 Agent 正在干的活；其他来源排队；短时间连发的多条消息合并成一轮处理
- Agent 循环必须放在服务器而不是虚拟机上，这样虚拟机可以独立重建（比如打安全补丁）而不中断服务

### Harness 与上下文工程

- 动态工具发现：不把所有工具的完整定义塞进上下文，只放工具名字，模型要用时再去读文件——省上下文也省钱（他管这叫 tool search）
- 成本阶梯：先用对话里已知的 → 查插件/API → 网页搜索 → 开浏览器 → 用整台电脑和脚本 → 实在不行才问用户；像个不会动不动打扰你的同事
- 浏览器取信息也有阶梯：无障碍树（accessibility tree）最省 token，其次 HTML，最后才是截图点像素；遇到验证码、二次验证才回头找用户
- 主 Agent（编排者）保持上下文稀疏，重活派给子 Agent，只收结果——这是"体感无限上下文"的来源；每个子 Agent 本身也是一个持久化工作流，崩了能独立重启
- 工程细节：回合中途不要增删工具（会破坏提示缓存）；某个动作 90% 都在用 shell 硬凑时，就该给它做专用工具；给 Agent 写的报错信息要像给人写的一样清楚（这是 Agent 版的 DX）
- 安全：每条 shell 命令先过自动审查（auto review）；邮件、webhook 等不可信输入绝不能当成用户指令（防提示注入）；发邮件这类不可逆动作必须先经用户确认；密码等秘密不进模型对话

### 上下文工程（≈ Harness 工程）

- 提示缓存是核心纪律：系统提示和工具定义保持静态、顺序固定（甚至按段做哈希管理），只有最新一条消息是未缓存的增量；缓存未命中就当 bug 修
- 小技巧：用户开始打字时服务器就预热缓存（像网页的 prefetch）；趁缓存还热（几十分钟窗口内）赶紧做上下文压缩，后续继续聊更便宜
- 压缩（compaction）不可避免且有损：长输出存文件而不是塞上下文；昂贵的活（如看截图）派给子 Agent，不污染主上下文；持续"修剪"对话
- 记忆分层：核心事实（每次必带）→ 按日期的工作日志 → 临时草稿笔记（短期有效）→ 其余一切靠文件 + 命令行搜索现查

### 他对未来的判断

- 训练飞轮：预训练 → 监督微调（教会在 harness 里工作）→ 强化学习（指令跟随、从几百个技能里选对的）；产品团队每天跑内循环（找 bug、修提示词和 harness、用评测量化），模型公司每几个月跑外循环（新模型吸收所有教训）
- Cursor / SpaceX 的一条原则叫"删掉产品"（delete the product）：假设今天的模型是史上最差的，为下一代模型做产品、尽量少造东西、保持界面简单
- 6–12 个月预测：Agent 连续工作数周到数月；记忆与回忆能力大幅提升；组织会愿意把全部工具交给这个"数字同事"；界面走向语音；"在岗学习技能"会非常强
- 没解决的问题：一个跑一个月的 Agent 怎么评测（模型每月都在换）；记忆的算法与表示（图？文件？）；安全的 harness；"该安静还是该打扰"的分寸；token 总量暴涨后的推理效率
- 收尾观点：每个应用都会有 Agent 的一面（类比 2005 年人人都在做服务器 + 数据库 + CRUD）；系统设计比以往更重要；要懂一点 LLM 的工作原理，就像做 Web 应用要懂数据库

## 核心概念速查

| 概念 | 一句话 |
|---|---|
| Agent | 模型在循环中调用工具、自主推进任务的主体 |
| Harness | 让 Agent 长期可靠工作的全部脚手架：工具管理、上下文、记忆、调度、安全 |
| 子 Agent（subagent） | 被主 Agent 派出去干专项活的独立对话，只回结果不回过程 |
| 持久化工作流（durable workflow） | 崩溃后能从断点续跑的长任务机制（代表工具 Temporal） |
| 上下文工程 | 对上下文窗口的刻意管理：缓存、压缩、分层、修剪 |
| 提示缓存（prompt caching） | 静态前缀复用，大幅降低重复发送整段对话的成本 |
| 压缩（compaction） | 把长对话总结成摘要以腾出窗口，有损但必要 |
| 自动审查（auto review） | 用另一个模型逐条审查待执行命令，替代人肉审批 |
| 动态工具发现（tool search） | 上下文里只放工具名，用时再加载完整定义 |
