## 总结

### 为什么安全在 AI 编码时代更重要

出发点很朴素：软件错误会摧毁用户对产品和公司的信任，并带来巨大的财务成本。而在今天，当 LLM 写了你的大部分代码时，你需要比以往**更广泛的防护栏（guardrails）**来防止这些错误。这里有个悖论：AI 编码工具提高了代码产出速度，同时也提高了引入漏洞的速度；而审查一段自己没亲手写的代码，比审查自己写的更难——人类工程师成了最后的安全防线。

### 现有的威胁图景：传统漏洞并没有消失

课程先列了经典的软件安全威胁清单（与 OWASP Top 10 一脉相承）：

- **SQL 注入（SQL injection）**：通过恶意输入拼凑、操纵数据库查询
- **跨站脚本（XSS）**：在网页中注入恶意脚本，在他人浏览器里执行
- **认证失效（broken authentication）**：登录与会话机制的缺陷
- **不安全的直接对象引用（IDOR）**：引用对象时不做授权检查，改个 ID 就能访问别人的数据
- **安全配置错误（security misconfigurations）**
- **敏感数据暴露（sensitive data exposure）**

要点是：这些老问题在 AI 时代一个都没少，只是代码产出更快后，更需要系统性的自动检测来兜底——这就引出三大检测技术。

### 三大漏洞检测技术：SAST、DAST、SCA

**SAST（静态应用安全测试，Static Application Security Testing）**

- **白盒**技术：不运行程序，直接分析源代码和二进制文件
- 发生在软件开发生命周期（SDLC）的**早期**——此时发现并修复漏洞的成本最低，这正是"左移（shift left）"理念的体现
- 能识别：SQL 注入、命令注入（command injection）、XSS
- 核心手法：对代码库做**模式匹配（pattern matching）**扫描——这也是 Semgrep 这类工具的基本路线

**DAST（动态应用安全测试，Dynamic Application Security Testing）**

- **黑盒**技术：不看代码，而是模拟真实攻击者从外部攻击一个正在运行的应用
- 可以贯穿整个 SDLC，且**假阳性更少**（因为报出来的问题是真的打进去了）
- 能识别：SQL 注入、认证失效、XSS
- 核心手法：输入模糊测试（input fuzzing）、操纵会话令牌（session token manipulation）、配置/响应头测试（configuration/header testing）、暴力破解速率限制测试（brute force rate-limit tests）

**SCA（软件组成分析，Software Composition Analysis）**

- 前两者查的是"你自己写的代码"，SCA 查的是"你用的别人的代码"：深度分析应用依赖的开源（OSS）包
- 分析对象包括包管理器、基础设施即代码（infrastructure-as-code）配置、拉取的容器镜像
- 核心手法：解析包元数据得到依赖关系；做**传递依赖解析（transitive dependency resolution）**——你依赖的包还依赖别的包，风险藏在深处；把依赖清单与已知漏洞数据库比对；对二进制/构建产物（artifact）做扫描

三者互补：SAST 在编码期从内部看代码，DAST 在运行期从外部模拟攻击，SCA 盯住供应链。完整的安全策略需要三者结合，单靠任何一种都有盲区。

### 变化之一：AI Agent 带来的新型攻击向量

这是本周最有时代感的部分。AI 不只是写代码的工具，Agent 本身成了新的攻击面，课程列了五种：

- **提示注入（prompt injection）**：在输入中藏入隐藏或误导性的指令，让生成式 AI 系统偏离预期行为——Agent 时代最核心的威胁
- **工具滥用（tool misuse）**：用欺骗性的 prompt 操纵 Agent 滥用它集成的工具，比如诱导它执行未授权的文件操作或 API 调用
- **意图破坏（intent breaking）**：操纵 Agent 的执行计划（plan），把它的行动从原始意图重定向到攻击者的目标
- **身份冒充（identity spoofing）**：利用被攻破的认证机制，冒充合法的 Agent
- **代码攻击（code attacks）**：利用 Agent 能执行代码的能力，获取对执行环境的未授权访问

传统软件的攻击面主要在输入验证和认证环节；Agent 的攻击面则扩展到 prompt、工具调用、执行计划、身份、执行环境五个维度，防护也必须在 prompt 过滤、工具权限控制、计划验证、身份验证、沙箱隔离多个层面同时展开。

### 变化之二：AI 也在改善检测

另一面是积极的：

- **"左移"比以往任何时候都更容易实践**：安全检查的门槛被 AI 拉低了
- **可以把 LLM 引入工作流来发现问题**：让模型在开发流程中做漏洞复核
- **自动化渗透测试（automated penetration testing）** 成为可能

### 但局限很严峻：假阳性、不可复现、上下文问题

课程对 AI 安全工具泼了冷水，这部分数字值得记住：

- **假阳性率极高**：在 AI SAST 中，Claude Code / Codex 的假阳性率可达 **50%–100%**（取决于漏洞类型）；作为对照，传统 SAST 技术的假阳性率也在 **50% 以上**。也就是说告警里一大半是误报，会严重干扰开发流程
- **基准不现实**：现有 benchmark 往往不反映真实场景，很难据此评估 LLM 的安全分析能力到底行不行
- **非确定性分析**：同一个 prompt 跑多次得到不同结果——那你怎么知道自己抓全了所有漏洞？"完整覆盖"在原理上就无法保证
- **上下文腐烂（context rot）**：并非所有 context 都同等有效，塞得多不等于看得准
- **压缩丢信息（compaction）**：为了把内容塞进上下文窗口而做的摘要压缩，可能恰好丢掉关键的安全细节

### 开放问题

课程最后留了六个没有答案的问题，基本就是这个领域的议程：

1. 如何降低漏洞检测中的假阳性和幻觉？
2. 如何验证 LLM 生成的补丁是安全的、且不引入回归？
3. LLM 能否解释它**为什么**标记某个漏洞、为什么提出某个修复？
4. 什么是衡量 LLM 应用安全（AppSec）性能的正确 benchmark？
5. LLM 应该如何嵌入 CI/CD，而不让噪音淹没团队？
6. 如果 AI 生成的补丁引入了漏洞，**谁负责**？

### 落到工程实践：把 AI 安全检查放对位置

讲义把课程内容往工程落地推了一步。关键不是多买一个"智能扫描器"，而是把 AI 放在合适的位置：

| 阶段 | 适合的 AI 安全动作 | 主要目标 |
|---|---|---|
| 编码阶段 | IDE 内联提示、局部静态检查 | 尽早阻止明显的危险模式进入代码库 |
| 提交阶段 | PR 级漏洞复核、依赖变更扫描 | 在合并前拦截高风险改动 |
| 测试阶段 | 自动化 DAST / fuzzing 辅助 | 发现运行时路径和环境相关问题 |
| 上线后 | 监控告警摘要、事故复盘辅助 | 缩短发现与定位时间，形成经验闭环 |

由此得出的策略是：把 AI 放在**"高召回、低决策权"**的位置——它负责尽可能早、尽可能全地暴露风险，最终裁决交给人类和硬性测试系统。这样既用上 AI 的覆盖面，又把假阳性和幻觉的噪音成本控制住。配套的团队建议包括：先把传统安全基线做好再引入 AI（不要拿 AI 当"没做安全工程"的替代品）；给 AI 告警设分级和升级路径，别让误报压垮团队注意力；对 AI 生成的安全补丁保留更严格的审查和测试门槛，尤其是认证、权限、支付链路。

### 事故响应视角：没有日志，AI 安全事故不可复盘

讲义还有一个实用提醒：安全不只是预防，也是响应。接入 Agent 的团队，事故处理流程要跟着变：

- 先确认问题来自传统漏洞、提示注入还是工具滥用——三者的修复路径完全不同
- 保留 Agent 的执行轨迹、prompt、工具调用日志和环境状态
- 区分"模型误判"与"系统权限设计错误"
- 把复盘结论写回规则、测试和权限边界，而不是只修一个表面 bug

传统 Web 服务至少有请求日志、错误堆栈、数据库审计；而 Agent 系统如果不记录 prompt、工具输入输出和关键中间决策，事后往往只看到错误结果，不知道它为什么这么做，修复只能靠猜。

## 核心概念速查

| 概念 | 一句话 |
|---|---|
| SAST（静态应用安全测试） | 白盒：不运行程序，靠模式匹配扫描源代码/二进制，在开发早期发现注入类漏洞 |
| DAST（动态应用安全测试） | 黑盒：模拟攻击者打运行中的应用（fuzzing、令牌操纵等），假阳性更少 |
| SCA（软件组成分析） | 查第三方依赖：解析传递依赖、比对漏洞数据库、扫描镜像与构建产物 |
| 左移（shift left） | 把安全检查尽量前移到开发生命周期早期，越早修越便宜 |
| 传递依赖（transitive dependency） | 你依赖的包再依赖的包，供应链风险常藏在这里 |
| 提示注入（prompt injection） | 在输入里藏指令，让 AI 系统偏离预期行为；Agent 时代的核心威胁 |
| 工具滥用（tool misuse） | 用欺骗性 prompt 诱导 Agent 滥用其集成的工具 |
| 意图破坏（intent breaking） | 篡改 Agent 的执行计划，把行动重定向到攻击者目标 |
| 身份冒充（identity spoofing） | 利用被攻破的认证冒充合法 Agent |
| 代码攻击（code attacks） | 利用 Agent 的代码执行能力入侵其执行环境 |
| 假阳性（false positive） | 误报的漏洞告警；AI SAST 可达 50%–100%，传统 SAST 也在 50% 以上 |
| 上下文腐烂（context rot） | 上下文并非越多越好，无效 context 会稀释分析质量 |
| 压缩（compaction） | 为塞进上下文窗口做的摘要，可能丢失关键安全细节 |
| 模糊测试（fuzzing） | 向程序喂大量随机/畸形输入，观察其异常行为，DAST 的核心手法之一 |
