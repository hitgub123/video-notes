## 总结

### 本周讲什么

第 2 周分两次课。周一课"从零构建 Coding Agent"：亲手写一个最小可用的编程 Agent，看清它的核心循环只有几步，然后拆解 Claude Code 这类成熟产品在循环之上加了哪些工程手段。周五课"To MCP and Beyond"：当每个 Agent 都要接外部工具时，集成方式本身成了问题，于是引入 Anthropic 2024 年 11 月推出的开放协议 MCP，看它如何把工具集成标准化，最后一节讲 MCP 当前的局限。

### 先厘清三个术语

- **System prompt（系统提示）**：定义 LLM 的整体行为和指令
- **User prompt（用户提示）**：用户的自定义请求
- **Assistant prompt（助手提示）**：LLM 的响应

一个 Coding Agent 本质上就是这三类消息加上一个工具集合，在循环里不断滚动。

### 最小 Coding Agent 的核心循环

课件的原话是"It's that simple"——构建步骤只有四步：

1. 从终端读取用户输入，持续追加到对话历史里
2. 告诉 LLM 有哪些工具可用（如 `Read_file`、`List_dir`、`Edit_file`）
3. LLM 在适当的时机请求调用工具
4. 你在本地（离线于模型之外）执行这个工具调用，把结果返回给模型，循环继续，直到任务完成；配合建文件、改文件的工具，它就能真的动手写代码

结论：**Coding Agent = LLM + 工具调用循环**，原理门槛很低。但一个能靠得住的 Agent，难点全在循环之外——上下文管理、防跑偏、子任务分解，这些正是下一节拆解成熟产品的原因。

### "秘密武器"：Claude Code 引擎盖下面有什么

课件直接把 Claude Code 当样本解剖，列了四个关键工程决策：

- **前置加载上下文（front-load context）**：用小而精准的提示词，把关键上下文提前塞好，而不是等模型缺信息了再补
- **System reminders 无处不在**：在 system prompt、user prompt、工具调用、工具结果里都插入 `<system-reminder>` 标签，反复提醒，防止模型在长对话中**偏离目标（context drift）**——讲义特别强调，长对话里 LLM 容易"忘记"早期指令和约束，这是经过工程验证的关键对抗手段
- **命令前缀提取（command prefix extraction）**：从用户输入中提取命令前缀，实现快捷操作
- **派生子 Agent（sub agents）**：把特定子任务分给子 Agent 处理，避免单个上下文过载

### 为什么需要 MCP：静态知识 + M×N 问题

周五课先问"为什么"。LLM 拥有海量但**静态**的世界知识，只在重新训练时才更新；而真正自主的系统需要动态数据——今天的天气、现任总统、比特币价格、Nike 最新广告的旁白是谁。课件的判断是：**RAG 和工具调用是今天最好的答案**。

但工具调用一旦规模化，集成方式就爆了。设想你要对接一个文档不全的第三方 API，光是搞清"它到底暴露了哪些接口"就够呛；当这样的 API 变成很多个、调用它们的 LLM 应用也变成很多个，问题彻底失控：

> 有 M 个 LLM 应用、N 个工具时，每个应用都要为每个工具单独写集成代码——认证、错误处理、限流全都重复实现——总共是 **M × N 个连接器**要维护。

### MCP 是什么：把 M×N 变成 M+N

MCP（Model Context Protocol，模型上下文协议）是一个开放协议，用通用化的方式向 AI 模型提供上下文——说白了，就是**向 LLM 暴露工具的标准格式**。它的核心价值：

- 集成从 M × N 降到 **M + N**：工具方写一次 Server，所有 Host 都能用；应用方接一次协议，所有 Server 都能连
- 认证、错误处理、限流等不必为每个工具重复实现
- 用 **JSON-RPC** 强制一致的输出格式
- 它从 **LSP（Language Server Protocol）** 扩展而来，但目标不同：LSP 是纯反应式的（编辑器问、服务器答），MCP 支持**主动的（proactive）agentic 工作流**

讲义用 LSP 做了个类比：LSP 没有发明"补全"或"跳转定义"，但它统一了编辑器与语言服务之间的接口，整个生态的创新速度因此被抬高；MCP 对 Agent 工具生态扮演类似角色——它统一的不只是调用语法，更是工具生态的**协作边界**：工具从某个项目的私有实现，变成生态的公共接口，用户切换工具、工作流跨产品迁移的成本都随之下降。

### MCP 架构与一次完整调用

四个角色：

- **Host（宿主）**：用户直接使用的应用，如 Cursor、Claude Desktop
- **MCP Client**：嵌在 Host 里的库，为每个 Server 维护一个有状态的会话（stateful session）
- **MCP Server**：套在某个工具外面的轻量包装器（wrapper）
- **Tool（工具）**：可调用的函数，背后可以是数据源或某个 API

工作流程五步：

1. Client 向 Server 调用 `tools/list`，问"你能做什么？"
2. Server 返回每个工具的 JSON 描述（名称、摘要、JSON Schema）
3. Host 把这些 JSON 注入模型的上下文
4. 用户提示触发模型，模型发出一个结构化的工具调用
5. MCP Server 执行调用并返回结果，对话继续

课件还给了一个流程图例子：用户说"总结一下 Jack 发给我的邮件"，Host 把查询发给模型并附上工具清单，模型挑中邮件工具并给出参数，Server 调用函数取回邮件，最后 Host 把结果回复给用户。传输层方面，MCP 提供 **stdio**（本地进程）和 **SSE**（远程服务）两种。课上还现场从零写了一个自定义 MCP Server，说明 Server 本身并不重。

### MCP 的局限（课件明说的三条）

- **Agent 现在处理不好"很多工具"**：工具一多，模型的挑选和调用质量明显下降
- **API 描述吃上下文**：每个工具的描述都要注入上下文窗口，工具越多、窗口被占得越快
- **API 要为 AI 原生设计，而不是沿用刚性设计**：讲义展开说，参数过多、嵌套太深、状态切换太隐式的接口会显著降低模型调用成功率；错误信息如果只有面向工程师的长堆栈、没有结构化原因，模型很难自行恢复；返回结果也更适合同时给摘要字段和机器可解析字段

### 讲义补充一：可维护 Coding Agent 的三层检查表

把本周两部分合起来看，讲义提出一个实践框架——一个能长期稳定工作的 Coding Agent，要同时过三关：

| 层 | 检查什么 |
|---|---|
| 模型层 | 系统提示词是否清楚说明任务、边界和工具使用原则 |
| 工具层 | 工具 schema 是否稳定、返回结果是否适合下一步推理 |
| 会话层 | 上下文是否会膨胀、是否有 reminder 机制、失败后如何恢复 |

第一节讲的上下文前置加载、system reminders、子 Agent 分流，都是在补当前模型做长任务时的脆弱性：Agent 不是会调用工具就够了，还必须在长时间、多步骤、多文件的工作里保持目标一致。

### 讲义补充二：不是所有问题都该"上一个 MCP Server"

讲义特意保留了一条工程判断：协议标准化降低的是接入成本，不替代系统设计——

- 底层 API 本身不稳定，MCP 只会把不稳定更标准地暴露出来
- 任务边界不清晰，模型就算能调用工具，也可能在错误的层面上自动化
- 缺少日志、重试和回滚时，协议统一反而可能放大错误的传播范围

所以课程一边讲协议，一边仍强调 agent loop、上下文管理和产品约束：可靠的 Coding Agent 不是"工具越多越好"，而是"能在明确边界内稳定完成任务"。

## 核心概念速查

| 概念 | 一句话 |
|---|---|
| Coding Agent | LLM + 工具调用循环组成的、能自主执行编程任务的系统 |
| System / User / Assistant prompt | 定义模型行为的系统指令 / 用户的请求 / 模型的响应，Agent 对话的三种消息 |
| 工具调用循环（agent loop） | 读输入 → 追加对话 → 模型请求工具 → 本地执行 → 返回结果 → 重复 |
| 上下文漂移（context drift） | 长对话中模型逐渐忘记早期指令和约束的现象 |
| System reminder | 插入在提示、工具调用与结果中的 `<system-reminder>` 提醒标签，用来防漂移 |
| 子 Agent（sub agent） | 主 Agent 派生出的分身，承接子任务以避免单个上下文过载 |
| MCP（Model Context Protocol） | Anthropic 2024 年 11 月推出的开放协议：向 LLM 暴露工具的标准格式 |
| M×N 问题 | M 个应用 × N 个工具各写一遍集成代码，连接器数量爆炸 |
| Host / Client / Server / Tool | 宿主应用（如 Cursor）/ 宿主内的协议库 / 工具外的轻量包装器 / 可调用的函数 |
| tools/list | Client 向 Server 查询可用工具清单的调用，返回名称、摘要与 JSON Schema |
| JSON-RPC | MCP 用来强制一致输出格式的消息协议 |
| stdio / SSE | MCP 的两种传输：本地进程通信 / 远程服务通信 |
| AI-native API | 为模型调用而设计的接口：参数扁平、错误结构化、结果带摘要 |
